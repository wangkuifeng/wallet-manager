# Enterprise Crypto Wallet System (CEX Architecture)

基于 **Go + Microservices** 架构的企业级中心化数字货币钱包系统。本项目实现了从用户开户、充值监听、风控审核到资金归集与冷热钱包调度的完整资金流转闭环。

---

## 🛠 设计原则

* **微服务架构 (Microservices)**：各模块职责单一，独立部署，互不影响。
* **私钥隔离 (Key Isolation)**：核心设计理念。**业务系统永远不接触私钥**，私钥仅由签名机（Signer）生成并加密存储，且 Signer 仅允许内网访问。

---

## 🏗 核心模块架构

系统对应代码库中的独立文件夹，核心模块如下：

| 模块名称 | 角色 | 核心职责 |
| :--- | :--- | :--- |
| **wallet** | 业务主模块 | 面向用户的前端 API，负责用户管理、账本记录，**绝不接触私钥**。 |
| **signer** | 签名机 | 系统的“保险柜”。负责地址生成、密钥管理及交易签名。**不联网或仅限内网访问**。 |
| **scan** | 充值扫描服务 | 系统的“眼睛”。持续监听链上交易并匹配用户充值。 |
| **risk_control** | 风控模块 | 系统的“保安”。检查交易是否存在风险（AML、确认数等）。 |
| **fund_rebalance** | 资金调度 | 系统的“管家”。负责资金归集（Sweeping）与多签钱包调度。 |

## 🚀 技术栈 (Tech Stack)

| 领域 | 技术选型 | 说明 |
| :--- | :--- | :--- |
| **开发语言** | **Golang** | 高并发、类型安全，原生适合区块链开发 |
| **Web 框架** | **Gin** | 用于构建 Wallet 和 Signer 的高性能 HTTP 接口 |
| **ORM 框架** | **Gorm** | 操作 MySQL 数据库，处理复杂查询 |
| **链上交互** | **go-ethereum** | RPC 通信、RLP 编码、ECDSA 签名 |
| **数据存储** | **MySQL** | 处理高频账本交易，依赖事务 (ACID) 和行锁 (For Update) |
| **安全加密** | **AES-GCM** | 用于在数据库中加密存储私钥 |

## 🔄 详细工作流程 (Workflow)

系统资金流转分为三个核心阶段：

### 第一阶段：开户与地址分配 (Onboarding)
> 用户与系统的第一次交互，建立账户体系。

1.  **用户请求**：用户在前端发起“获取充值地址”请求。
2.  **业务转发**：`wallet` 服务接收请求，校验用户资格。
3.  **远程调用**：`wallet` 请求 `signer` 的内部接口 `/keys/create`。
4.  **密钥生成 (在 Signer 内部)**：
    * 生成一对公私钥 (ECDSA)。
    * **私钥**：使用 AES-GCM 加密后存入 `secure_signer` 数据库（永不离开 Signer）。
    * **地址**：返回给 `wallet` 服务。
5.  **绑定关系**：`wallet` 将返回的地址与 UserID 绑定，存入业务数据库，并展示给用户。

### 第二阶段：充值与入账 (Deposit & Accounting)
> 资金从区块链进入系统的全过程。

1.  **用户转账**：用户向分配的地址转账（例如 10 ETH）。
2.  **链上监听 (scan)**：
    * `scan` 服务死循环轮询最新区块。
    * 匹配交易的 `To` 地址是否在系统白名单中。
    * 发现匹配交易，写入 `user_deposits` 表，标记状态为 `Status=0` (待处理)。
3.  **风控审核 (risk_control)**：
    * `risk_control` 服务轮询待处理记录。
    * **确认数检查**：确保区块高度 > 6-12 个块（防分叉/回滚）。
    * **黑名单检查**：确保资金来源地址不在 AML 黑名单中。
    * **金额检查**：确保单笔金额未超过风控上限。
4.  **正式入账**：
    * 风控通过后，开启数据库事务。
    * 更新 `user_deposits` 状态为 `Success`。
    * 原子更新 `user_accounts`，增加用户余额 (+10 ETH)。
    * 用户 App 端余额更新，可进行交易。

### 第三阶段：资金归集与调度 (Sweeping & Rebalancing)
> 系统内部资金整理，用户无感知。

#### 1. 自动归集 (User -> Hot Wallet)
为了防止资金分散，系统需将用户地址的资金归集到热钱包。
* **触发条件**：`fund_rebalance` 服务检测到某用户地址余额 > 0.1 ETH。
* **构造交易**：生成一笔 `From: 用户地址` -> `To: 热钱包` 的交易。
* **签名请求**：调用 `signer` 的 `/sign_tx` 接口。
* **签名与广播**：`signer` 解密私钥并签名，返回签名后的 Tx 数据；`fund_rebalance` 服务广播交易。

#### 2. 热钱包水位监测 (Hot Wallet Check)
维持热钱包流动性，同时保障大额资金安全。
* **情况 A：水位过高 ( > 50 ETH )**
    * **动作**：系统自动触发转账，将超出部分转入 **冷钱包** (Cold Wallet)。
    * **目的**：安全存储，冷钱包私钥离线保存。
* **情况 B：水位过低 ( < 10 ETH )**
    * **动作**：系统发出 **严重警报** (Slack/邮件/日志)。
    * **目的**：通知财务人员手动从冷钱包打款至热钱包，确保后续的用户提现顺畅。
